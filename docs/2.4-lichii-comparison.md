# 2.4: Lichii comparison (source level)

Reference: [zortos293/Lichii](https://github.com/zortos293/Lichii), branch `nx2`, commit
`b198feba3466c2bae1cd45e63d212f6b649c0902` (2026-11-21, "hwacod: EDEN_NX2_HWACOD_TRACE logs
instances and per-second tasks by instance (#2367)"). Compared against Veshiru `2.3.0`
(`0c8f66ec1f9657a5c06d0a748bad38398cb7ffbf`).

No emulator was run for this comparison: the agent environment has no GPU, no game files and no
Vulkan driver, so everything below is read from source and from the two logs supplied with the
request. Runtime claims are marked as such.

Veshiru generates 1.4–2.7 extra frames per real frame in the heavy scenes; Lichii generates
0.3–1.1. Both runs are in different scenes and settings (`mkw_60fps` is on in the Lichii run,
`mkw_dynamic_fps` is on in the Veshiru run), so this is not a like-for-like FPS measurement. It
does explain the direction of the user's observation: Veshiru asks the GPU for more synthesized
frames, and on a 4 GB 1650 that work competes with the native frame.

## Table

| Area | Lichii (nx2 `b198feb`) | Veshiru 2.3.0 |
|---|---|---|
| Optical-flow algorithm | Block matching in a compute shader (`frame_gen_optical_flow_comp`): fixed `search_radius=2`, `block_size=2`, shared-memory tiles, early-out for static pixels, duplicate-frame detection; bilateral interpolation pass at output resolution. | Learned "NanoModel" (Open-Frame-Gen): prep, three depthwise/pixelwise encoder stages, skip decoder, head and a full-resolution warp pass, with per-pass push constants. Heavier per frame, better handling of occlusion and fine detail. |
| Flow resolution | Half output resolution (`m_flow_extent = extent / 2`), interpolation at full resolution. | `flow_scale` 0.25–1.0 with a VRAM-aware cap: base flow pyramid ≤640×360 at ≤6 GiB VRAM, ≤768×432 above; the warp is still full output resolution. The 2.3 log shows the 1650 picking the 640×360 cap. |
| Cost control | One flow dispatch plus one interpolation dispatch per generated frame; no probe/hysteresis logic in the pacer. | Per-level probing with backoff, sustained-slow and isolated-hitch skips, `GenerationsWithoutWaiting(free_frames - 1)` so FIFO backpressure can never hold the native rate, and a target-rate pacer (`frame_gen_pacer.cpp`). |
| Pacing | `FrameGenPacer` from the same Eden lineage: smoothed interval, 1→2→4→8 s probes, one-step limit changes. | Same pacer plus per-level failure tracking, probe step deferral, deficit/surplus hysteresis, display-trim accounting, and hitch-skipped plans that preserve flow history. |
| Avoiding native-FPS loss | Steps generation down when the display cannot take more presents; no data for a limit on generation work when the game is already slow. | Same rule, plus `MINIMUM_BASE_RATE = 10 FPS` and a 3-consecutive-slow-frame sustained-slow path; isolated hitches skip generation without poisoning the probe. |
| Blur / ghosting | Bilateral interpolation weighted by flow confidence; duplicate-frame detection avoids flow on static frames. | Learned warping plus blend/sharpness push constants; fractional-cadence skip frame captures history without generating. |
| UI-element artefacts | No UI mask; the whole frame is treated the same. | No UI mask either. The window-adapt pass and post-process graph are separate from frame gen; generated frames are labelled cosmetic. |
| Stability / recovery | Fixed two-pipeline setup; no explicit device-support pre-check beyond shader compilation. | `open_frame_gen_policy.h` checks format features, formatless writes and dispatch limits before building; pipeline failure falls back to LSFG; HDR is refused for Open-Frame-Gen; `blocked_config` remembers a rejected configuration. |
| VRAM management | Full-resolution history + current frames, half-res flow; no device-local budget awareness. | Flow pyramid cap derived from `GetDeviceLocalMemory()`; 2.3 buffer cache reports ~425 MiB for MKW; texture cache host spill is tracked with margins. |
| Game list / UI polish | Ryujinx-style tree/grid; no Versioned List. | Versioned List (rebuilt in 2.4), carousel, grid, version badges, missing rows. |
| Notifications | None. | 2.4 adds a tray icon and Veshiru-icon toasts. |
| RPC | Eden's discord-rpc SDK with Eden's client ID, cover art fetched from a community repo. | Own minimal IPC client; 2.4 embeds an application ID, sends title/version/elapsed time and a Veshiru icon only. |
| Update flow | Built-in checker, Forgejo-era dialog string. | GitHub release checker and updater with checksum validation; 2.4 points the news applet and doc links at GitHub. |

## Was anything ported?

Nothing was ported for 2.4. Every candidate in the brief is already present in Veshiru 2.3, in a
more developed form than Lichii's:

- reduced-resolution flow pass — already there, with a VRAM-aware cap;
- skip generation when the frame budget is blown — already there (`hitch_skipped`,
  `SUSTAINED_SLOW_FRAMES`, `MINIMUM_BASE_RATE`);
- even pacing — already there, with a more elaborate pacer than Lichii's;
- lower VRAM for flow buffers — already there (14 MiB base pyramid at 640×360 vs ~57 MiB at
  720p, per the `ComputeNanoExtent` comment).

The one Lichii behaviour Veshiru lacks is cheaper flow (half-res block matching). Porting it would
replace a better-quality path with a worse one, which the brief forbids, and there is no
target-hardware measurement in this environment to justify a new quality/cost trade-off. No
Vulkan/perf source was changed in 2.4.

## What would need measuring before a 2.5 perf change

1. Same scene, same save, same settings: frame gen off vs Lichii-style half-res flow vs current
   Open-Frame-Gen, recording native FPS, 1% lows, generated FPS, and GPU busy time.
2. Whether capping generated frames per real frame at 1.0–1.5 on ≤6 GiB GPUs helps native FPS at
   12–20 FPS. The 2.3 log's 2.6 generated/game frame at 12.2 FPS is the case to test.
3. Whether the NanoModel passes can overlap with the next frame's guest GPU work on Turing's
   compute-only queue, or whether the 1650 serialises them anyway.
4. Flow buffer VRAM at 1080p and 1440p output on the 4 GB card, using
   `Texture cache TickFrame` / host-spill lines as the source of truth.
