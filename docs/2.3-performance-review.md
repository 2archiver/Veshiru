# 2.3 performance and privacy review

## What the supplied log establishes

The attached 2.2.0 session contains repeated gameplay windows with roughly 13–15 native frames/s,
600-present windows averaging about 70–73 ms per frame, and occasional frames taking over a second.
Other windows rise substantially, so this is not a single steady-state workload. Open-Frame-Gen's
queued presents vary widely; generated presents do not mean the game simulation is running at that
rate or at normal speed.

The useful clues are:

- The logged GPU-fence wait is usually near zero, while hundreds of guest CPU reads per ten seconds
  include dozens to more than one hundred synchronous GPU waits. Their average wait is commonly
  below 1 ms but individual waits reach tens of milliseconds. This is a plausible source of frame
  spikes, not proof that all of the slow frame is caused by readback.
- A small number of pipelines are still being built after boot. Reported draw holds in the shown
  intervals are in the low hundreds of milliseconds per ten seconds. That can cause hitches, but
  does not account for a sustained 70 ms average frame by itself.
- The trace does not contain the per-thread CPU/GPU profile needed to distinguish a saturated guest
  thread, expensive GPU work, power/thermal limits, storage stalls, or contention. It therefore
  cannot support a safe change to shader accuracy, clocks, memory behavior, or scheduler policy.

Frame generation, a faster refresh setting, and list refresh behavior cannot increase the native
simulation rate. A stable 30 FPS target needs a repeatable same-scene baseline and an A/B test with
the profile tools in `AGENTS.md` (`EDEN_NX2_GPU_PROFILE`, `EDEN_DKB_FRAME_TRACE`, and, where needed,
`EDEN_NX2_GUEST_THREAD_STATS` / `EDEN_NX2_ACQUIRE_STATS`). No target-machine gameplay run or
before/after FPS measurement was available for this change, so no 30 FPS result is claimed.

## Privacy fix from this log

The uploaded log printed emulated unit and battery serials and the selected host network adapter
name in settings dumps. Values such as these, plus device/account labels, user-configured endpoints,
controller/audio identifiers, and the recommended-settings backup, are now redacted in settings
logs. IPv4 and MAC addresses are also scrubbed from log messages. Setting labels remain so
diagnostics can still show which setting is involved.

## 3.7: address redaction is now a single-pass scanner

The previous implementation ran two `std::regex` passes over every log line (any dotted quad was
redacted as an IPv4 address, so `Vulkan 1.3.280` and driver `551.86.0.0` lost their numbers).
`common/address_redaction.h` replaces both with one hand-written scan:

- IPv4: four octets of 0-255, no leading zeroes, digit/dot/letter boundaries, no fifth component,
  and no version word (v, version, driver, Vulkan, API - case-insensitive, word-bounded) in the
  twelve characters before it.
- MAC: six hex pairs with one consistent `:` or `-` separator and hex/separator boundaries.
- IPv6: eight groups, or at least three groups with exactly one `::`, one to four digits each.
- Lines without `.`, `:` or `-` skip the scanner entirely.

The unit test (`src/tests/common/address_redaction.cpp`) covers the required cases: 192.168.1.20,
10.0.0.1:443, fe80::1ff:fe23:4567:890a and AA:BB:CC:DD:EE:FF are redacted; 1.3.274.1,
Vulkan 1.3.280, driver 551.86.0.0, v2.3.0, 999.1.1.1, 1.2.3.4.5, 12:34:56 and title IDs are not.
Its benchmark prints both timings for 100,000 typical log lines and asserts nothing about them, so
CI timing noise cannot fail a build. Local measurement on the development container: 1578 ms with
the two regexes, 46 ms with the scanner for the same 100k lines (~34x on that machine). That ratio
is reported, not claimed as a user-visible speedup: log redaction was never a frame-time cost.

## 3.8: storage-binding cache generation audit

Every increment of `map_serial` (the serial the storage-binding cache compares) happens in exactly
two places, both the final statement of the function that owns that page-table mutation:

| Increment site | Function | Reached from | Counter effect |
| --- | --- | --- | --- |
| `src/video_core/memory_manager.cpp:176` | `PageTableOp` | `Map` (small pages), `MapSparse` (small), `Unmap` (small pass) | `map_serial` +1, `mapping_updates_started/completed` +1 |
| `src/video_core/memory_manager.cpp:241` | `BigPageTableOp` | `Map` (big pages), `MapSparse` (big), `Unmap` (big pass) | `map_serial` +1, `mapping_updates_started/completed` +1 |

`Unmap` runs both operations over the freed range and therefore advances the generation by two.
A range rejected for lying outside the GPU address space returns before either increment: it
changes no page table and must not invalidate caches. No other code path in the repository edits
the GPU page table; there is no bypass to fix, and `src/tests/video_core/memory_manager_runs.cpp`
now pins this: `Map`, `MapSparse`, `Unmap` and a remap over live pages each advance
`StableMappingGeneration` and `MapSerial` in lockstep, an out-of-range `Map` advances neither, and
the generation stays `nullopt` (cache bypassed) until an update completes.

How the cache uses it (`src/video_core/buffer_cache/buffer_cache.h:4492`): the hit loop runs only
when `StableMappingGeneration` returned a value, and a stored serial must equal that generation.
A binding obtained mid-update cannot be mistaken for current because the in-flight op holds
`started` ahead of `completed`.

Residual, not fixed: the generation covers GPU page-table updates only. A device-memory remap
that did not go through a GPU page-table op would not by itself invalidate the cache; the cached
`Binding` would then hold a stale `buffer_id`. Every such path we found (guest memory freed under
a live GPU mapping) also runs the rasterizer invalidation that rebuilds the affected buffers, and
requires malformed guest behavior (leaking the GPU mapping) to reach at all. This exposure is
inherited from the pre-2.3 cache, which had no serial check whatsoever; it is documented here
rather than fixed blind, because folding `DeviceMemoryManager`'s `translation_generation` into the
binding serial needs its own measurement of the per-draw cost. Map→bind→unmap→remap reuse across
a generation change is covered by the lockstep test above: the changed generation forces a miss
and a fresh binding.

## 5.1: the performance summary

`video_core/perf_summary.h` adds a privacy-safe measurement window so before/after comparisons
take minutes instead of a profiling session. One Info line per window, fixed field order:

```
perf: window=10.0s native_fps=14.2 ft_p50=68.1 p95=94.0 p99=140.2 low1=112.0 low01=410.5 gt33=141 gt100=9 syncwait=87/312.4ms pipe_builds=3 genpresents=0
```

- **Frame time** is the native present-to-present interval. Generated frames are excluded from the
  percentiles and counted in `genpresents`.
- **low1 / low01** are the mean of the slowest 1% / 0.1% of frame times in the window;
  `low01` prints `n/a` with fewer than 1000 frames. Percentiles are nearest-rank.
- **syncwait** counts guest CPU reads that waited for a synchronous GPU flush (count/total time).
- **pipe_builds** counts pipeline builds of every kind that finished in the window.
- Off by default. Debug > Performance Summary (off / 10 s / 30 s, persisted) or
  `VESHIRU_PERF_SUMMARY=<seconds>`; Ctrl+F10 dumps one window on demand. A `perf flags:` boot
  line names every performance switch the session runs with.

When off, `OnPresent` and both counters return on a single atomic load, and the frame ring is
fixed-size storage with no per-frame allocation.

## 5.3: next steps toward 30 FPS, ranked

The 2.2.0 baseline on the reference machine (i7-10750H, GTX 1650 4GB) is ~13-15 native FPS with
~70-73 ms average frames and spikes over a second. Ranked by expected value, each with the
measurement that would justify it:

1. **Same-scene profiling with the 5.1 summary and the existing trace switches.** Before any
   change: capture a 3x30 s baseline window in one reproducible scene with
   `EDEN_NX2_GPU_PROFILE` and `EDEN_DKB_FRAME_TRACE` alongside the summary. Everything below is
   a hypothesis until this exists.
2. **The synchronous-readback tail.** Hundreds of guest CPU reads per 10 s with dozens to 100+
   synchronous GPU waits (average <1 ms, tails in the tens of ms) line up with the spike
   distribution. Candidates: batch or defer flush-triggering reads, and overlap the wait with
   queued GPU work. Measure via `syncwait` dropping and `p99`/`gt100` narrowing.
3. **Shader pipeline build hitches.** Post-boot pipeline builds in the low hundreds of
   milliseconds per 10 s. Extend the existing pipeline cache hit rate before adding threads:
   measure `pipe_builds` per window against a warmed cache.
4. **Frame pacing around present.** The trace shows host pacing variance; frame generation does
   not raise the native rate. Revisit only after 1-3, with `ft_p50` vs `p95` separating render
   cost from pacing jitter.

**A/B protocol (5 minutes per side):** same save, same scene, 60 s settle, then three summary
windows; compare medians of `native_fps`, `ft_p99`, `low1` and `syncwait`. No change may be
described as an FPS improvement without this measurement on the same scene.

## 4: incremental library refresh

Game-list refreshes now log
`library refresh: N entries, X reused, Y parsed, Z ms (reason: <settings|watcher|startup>)`.
The parse cache is in memory for the session, keyed by canonical path + file size + mtime;
play time is re-looked-up when a row is rebuilt, and the manual content provider is still
refilled on every scan so boot support never depends on the cache. The cache is cleared when
decryption keys or firmware are installed and wherever the on-disk metadata cache is cleared.
Settings refreshes stay immediate; watcher bursts go through the 30 ms debounce.
