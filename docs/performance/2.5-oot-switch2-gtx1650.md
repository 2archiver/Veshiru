# 2.5.0 — Ocarina of Time (Switch 2) on the Metabox NH77DB (GTX 1650 4 GB)

configuration and follow-ups that matter for this machine: **Intel i7-10750H (6C/12T, 2.6 GHz
base), NVIDIA GeForce GTX 1650 (4 GB, 3935 MiB device-local), 31.8 GiB RAM, Windows 11 26H2,
firmware 21.2.0, Veshiru v2.4.1 (commit 2fc3c41)**.

The game is **The Legend of Zelda: Ocarina of Time (0400486024DEC000, v2.0.0, 64-bit)**, a
Switch 2 title. Companion data comes from Mario Kart World (0400C3F00006E000, v1.8.0,

Measurement protocol for the first 2.5.0 session on the NH77DB (keep settings identical to
2.4.1 except the ones under test):

1. Wipe Studio/per-game overrides except the documented ones; set `texture_cache_memory_limit=0`,
   `precache_shaders=Ask`; keep `gpu_accuracy=Low`, `gpu_resolution=Res1X` and frame generation
   **off** for the measurement run.
2. Cold start the HOME applet, record `last 600 presents` lines there and during the first OoT
   boot (note time-to-first-present).
3. Walk into Kakariko immediately; grep the log for `last 600 presents`, `Runtime pipelines in the
   last 10 s`, `Frame generation (FSR3` and `Trimmed` lines. Repeat the walk once with a warm
   cache (second boot of the day).
4. Report the average/worst frame time and the over-100 ms count per window — those three
   numbers are the release evidence.

## TL;DR

1. **The stutter on entering heavy scenes is on-demand pipeline compilation, not the GPU and not
   vsync.** Draws were held waiting for pipelines up to **7.8 s per 10 s window** (78 % of wall
   time) during one Kakariko walk-through, and a single 10 s window held **21.0 s** of draws on
   first entry (111veshiru log), with one frame stretching to **39.4 s**.
2. **Kakariko's ~10 FPS is the emulated CPU plus those compilation holds.** `blocked on the GPU
   fence` averages ~0 µs in every window — the present thread never actually waits for the GPU.
3. **Frame generation does not rescue this.** At 8–25 real FPS the FSR3 path adds latency and
   memory pressure without giving back smoothness; it is designed for ≥ 30 FPS.
4. **`sync_core_speed` is now on by default in 2.5.0** (it makes the guest clock follow the
   speed limit instead of the raw host clock; the game no longer runs faster than it should).
5. **VRAM is the 4 GB card's hard ceiling.** `ResolveLimit()` clamps an explicit
   `texture_cache_memory_limit` to the device's total memory, so the per-game value 3935 is
   "no limit": the cache may fill the whole card. Set it back to 0 (Auto = 3/4 of the device,
   about 2.9 GiB) or 2048-3072. This will not make Kakariko faster, but it stops the driver
   thrashing.
6. **After one session the cache is materially warmer** (this session recorded 146 new
   programs; the next boot builds them at load instead of mid-frame). Play the village once,
   expect the worst first-visit freezes to disappear; they will not fully vanish on a cold
   cache, and no GTX 1650 will make this scene a steady 60 FPS.

### CPU readbacks (guest wants data the GPU has)

veshiru_log.txt, per 10 s: up to **189 reads** (avg sync wait 3 902 µs, max 62.9 ms) at 01:37,
173 reads (avg 3 146 µs) at 01:57, 50–66 reads (avg 2.1–4.6 ms) through 02:52–03:13, 57 reads
(avg 4 180 µs, max 46.5 ms) at 04:13. These are small transfers (0.12–0.74 MiB) — the cost is
the wait, and it concentrates in the same windows as the pipeline builds.

### The 05:03 TrimZeroPages line

`Trimmed 831 MiB of all-zero guest pages out of 8479 MiB resident in 1983 ms` (HW.Memory, at
03:51). The pass scans the whole working set and takes ~2 s on this host. It is a background
thread at Low priority and it deliberately defers during bulk mapping; on a 32 GB machine the
default thresholds let it run mid-scene. It did not cause the 10 FPS, but it lands as a
~2 s CPU-side noise during the village visit and inflates worst-case frame times.

### Video decode ("late dropped")

`nx2:vdecsvc … late dropped` climbs to 539 over the session (the opening FMV). The decoder
drops frames a later frame has already overtaken — by design. The drops are downstream of the
game running at 10 FPS, not a decode fault; `nvdec_emulation: Gpu` (the recommended setting,
used here) is already the right choice. Fix the frame rate and the drops fix themselves.

### Frame generation and pacing behaviour

* With `use_vsync: Fifo` at 60 Hz the present thread paces to each 16.7 ms boundary
  (`vblank pacing ≈ 14.3–15.6 ms` per frame at 60 FPS). At 10 FPS the pace line drops to
  ~1.5 ms — the game arrives late anyway; pacing is not the limiter.
* Frame generation idles at 59.1 FPS out of the village and never reaches its 60 FPS target
  inside the village. `frame_gen_target_rate: 60` with `multiplier: 2` wants ≥ 30 real FPS as
  input; feeding it 10 buys judder and a couple of extra buffer allocations, not frames.

### Memory and VRAM

* NUP decompression cache pinned **1536 MiB** of RAM.
* Guest working set peaked at **8 479 MiB resident** (trim pass log line) — the 4 Gb memory
  layout, as expected for a Switch 2 title.
* Buffer cache peaked at **664 buffers / 434 MiB**; texture cache limit was set per-game to
  **3935 MiB** — i.e. the entire GTX 1650. Frame generation (FSR3 flow, history and output
  images) and the driver's own caches then compete for the remainder.
* `Native compute storage bindings` with sizes past 8 MiB: 615–1071 per 10 s window (largest
  0x47c6000 ≈ 75 MiB) — reported for information; not itself a host allocation.

### Reference: Mario Kart World (2veshiru_log.txt.old.txt, Open-Frame-Gen)

Same pattern, same ceiling: steady 16.7 ms frames in light scenes, ~52–94 ms in heavy ones,
`100 over 100 ms` windows at 87–94 ms (≈ 11 FPS), max single frames of 0.6–5.1 s. Nothing
game-specific about "heavy Switch 2 scene on a 4 GB Turing (TU117) GPU" is fast; the fixes
below are not OOT magic.

## Root causes, in order of contribution

1. **Cold on-demand pipelines.** 131 new pipelines built at runtime; before this session they
   had never been seen, so no cache (disk or driver) could supply them. Each costs 250–1 100 ms
   of worker time on the i7-10750H and the GPU thread holds the draws meanwhile.
2. **Draws held instead of dropped.** `native_async_draws: Bounded` (the recommended setting;
   correct) bounds the wait to `native_pipeline_wait_ms` (8 ms) per draw and then holds the
   draw anyway for native work that fails the depth/history predicate — Ark's build logs the
   hold as the "draws held" figure. Skipping would sacrifice correctness for speed and is not
   a free lunch.
3. **A 4 GB card running a game sized for 10+ GB.** Texture eviction and reload, driver cache
   pressure, and frame-gen allocations all fit in that budget poorly.
4. **The emulated CPU.** 10 FPS in a dense scene with the GPU idle (fence wait ≈ 0 µs) is the
   i7-10750H IPC ceiling against Switch 2 A78C-class heavy lifting; no setting changes that.
5. **Everything else is downstream**: video drops, FG starvation, pacing quantization,
   TrimZeroPages noise.

## What 2.5.0 changes in code

* **`sync_core_speed` defaults to true** (settings default, first-run seed and the recommended
  table agree; `first_run_config` test updated). The guest clock now follows the speed limit,
  so the game cannot run ahead of itself when it is faster than real time — Ark's "game speed a
  bit faster than it should be" note. Existing INI values are not rewritten; only fresh
  profiles and "Use recommended settings" get the new default.
* **The HOME applet news feed shows the Veshiru icon.** The built-in/fallback banner images
  are now embedded JPEGs (800×450 and 320×180 from `dist/branding/veshiru_icon.png`,
  regenerable with `tools/ci/embed-news-images.py`); the news topic id is `veshiru`; nothing
  is fetched from eden-emu.dev any more, so the icon loads offline and never shows another
  project's logo. Menu staleness/empty-state behaviour is unchanged.
* **Discord Rich Presence payload is 100% Veshiru** (`details`: "Playing <title>",
  `state`: "Veshiru <version>[ - Version <game version>]", `large_text`: "Veshiru",
  large image served from this repo) - the only Eden-labelled element left is the bold
  application name above it, which is stored on Discord's servers with the application the
  client ID belongs to. No code change in the emulator can rename it.
* **This document.**

## Recommended configuration for this machine (per game, Configure → … → Per-game)

Keep the global/recommended profile; apply these to OOT (0400486024DEC000):

| Setting | Value | Why |
| --- | --- | --- |
| `texture_cache_memory_limit` | **0** (Auto, = 3/4 of device memory, about 2.9 GiB) or **2048-3072** | `ResolveLimit()` clamps any explicit limit to the device total memory, so 3935 on this card is exactly "no limit": the cache may fill the whole GTX 1650. Auto keeps about 3/4 and leaves room for the driver and the game. Costs extra texture reloads on scene changes. |
| `precache_shaders` | **Ask** (or Always) | Builds every recorded pipeline at boot instead of mid-village. First boot after recording is slow; every later boot is clean. `Always` skips the prompt. |
| `native_pipeline_wait_ms` | **8** (keep) | The bounded wait is already short; raising it converts dropped draws into freezes without buying throughput. |
| `gpu_accuracy` | **Low** (keep) | Correct trade for this card. |
| `native_async_draws` | **Bounded** (keep) | `Skip` drops real draws; only worthwhile for a slideshow. |
| `frame_gen` | **Off inside the village, on outside** if desired | At 10–25 real FPS it adds latency and allocations. If left on, keep multiplier 2 and target 60. |
| `frame_gen_target_rate` | **60** (keep) | Only meaningful if the game reaches ~30 FPS. |
| `use_vsync` | **Fifo** (keep) | Simplest correct pacing; `Mailbox` trades tearing for latency. |
| `nvdec_emulation` | **Gpu** (keep) | The recommended value; CPU decode falls over on EOTs C motion. |
| `vram_usage_mode` | **Conservative** (keep) | The recommended value for 4 GB cards. |
| `use_asynchronous_shaders` | **true** (keep) | Nothing else to gain here for pipeline builds. |

Host-side housekeeping:

* Close the driver-hungry extras (browser hardware acceleration, capture tools). The GTX 1650
  is sharing 4 GB.
* Keep `.cache/shader_cache_v2` and the driver pipeline cache between sessions — deleting
  them resets Kakariko to first-entry behaviour.
* If the trim noise is unwanted on 32 GB hosts, the zero-page trim is worth watching in the
  log; there is no user-facing toggle yet (see "Open items").

## What this machine will and will not do

Realistic expectations, from the logs rather than from wishful thinking:

* Out-of-village gameplay is already full-speed (59.9 FPS). **Keep it that way**: the fastest
  Kakariko fix is the cache, and the cache improves with every session.
* Kakariko in 2.5.0 with a warm cache: the missing pipelines are now in the shader cache v2
  and the stock drivers' caches, so the 20-second compilation storms should not recur.
  [unverified: needs one clean session on Ark's machine]
* Kakariko on a first-ever visit will always stutter on this hardware. The only cures are
  precaching at boot (the `precache_shaders` Ask/Always above) or staying out of the village
  until the cache warms.
* A steady 60 FPS in the village is not on the table for an i7-10750H + GTX 1650. A steady
  10+ real FPS — Ark's own target — is achievable when the pipeline holds go away.
* Frame generation: treat as a cosmetic multiplier above ~30 real FPS. Below that, it is
  overhead.
* MKW heavy scenes behave the same; nothing in this document is specific to Zelda.

## If you want more (open items, ordered)

1. **Verify the warm-cache path on Ark's machine** and record the before/after
   `last 600 presents` lines for the village. This is the one number that matters.
   [unverified]
2. **Consider `precache_shaders: Always` as the default for titles with a warm cache** —
   2.5.0 keeps the recommended table at `Off` (it is the right default for a cold cache and
   for boot time), but a per-game default of `Always` for OOT is defensible. [product
   decision, not a bug]
3. **TrimZeroPages on ample-RAM hosts**: the 05:03 pass read ~8.5 GB and took ~2 s. A
   longer-lived idle-only policy (only trim while the game is paused or the window is
   unfocused) would remove the noise without giving up the memory. [needs repro and
   measurements on a paused game]
4. **The one 39.4 s frame** (111veshiru log, Kakariko entry): 78 pipelines built in 10 s is
   the proximate cause, but a single-frame 39 s spike also smells like a flush/fence storm —
   worth a `stutter_trace=1` session to split compilation from sync. [investigation]
5. **Async build latency on this driver**: individual worker builds of 250–1 100 ms are what
   make compilation stalls user-visible even with `native_async_draws: Bounded`. Stage-cache
   hits already cut most of that; the remaining driver cost is current NVIDIA Game Ready drivers on TU117.
   [vendor/driver matter]
6. **Skip-on-unbuilt for native depth-tested draws is already implemented** (`Bounded` wait
   then draw-or-skip per the depth/history predicate). Turning the wait into a hard skip
   (`native_async_draws: Skip`) removes the holds but will drop real draws; do it only for
   a slideshow diagnostic.
7. **FXSave/branch prediction of the loop**: nothing to do here; Dynarmic is the shipped
   backend and changing that is a research project, not a patch.

## Monitoring cheatsheet

Watch these lines after a change; they answer "is it fixed?" in one grep:

```
nx2:vi2 last 600 presents: frame <us> (max <us>, <n> over 100 ms) …
Runtime pipelines in the last 10 s: <n> built … <ms> of draws held for unbuilt pipelines
CPU readback summary (10 s): <n> reads (<n> sync GPU waits … max sync wait <us>) …
Frame generation (FSR3 …) active: <fps> game FPS, … <n> hitch skips …
HW.Memory … Trimmed <mib> MiB of all-zero guest pages out of <mib> MiB resident
Shader cache v2 programs: <n> from records … <n> lowered
```

Green for the village: frame ≤ ~110 000 µs, 0–20 over-100 ms frames, "draws held" ≈ 0 ms for
three consecutive windows, and "hitch skips" ≈ 0 — at which point frame generation becomes
meaningful again.
