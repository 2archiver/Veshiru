# Benchmark contract for measurement claims (2.5.0+)

No number may be quoted as a 2.5.0 improvement unless this contract was followed. The five
logs this release shipped with are **not** compliant captures (no transition markers, no
frame-gen-off gameplay segments, mixed firmware/settings) — treat them as hypotheses.

## Hardware and environment (fixed for a series)

- Same machine (Metabox NH77DB class: i7-10750H, GTX 1650 4 GB, 32 GB RAM recommended ≥24 GiB free).
- Same Windows build, same GPU driver (record `nvidia-smi --query-gpu=driver_version`), same AC/output state, same display and refresh rate, same V-Sync mode.
- Same title, same title version, same save, same route, same settings, same firmware.
- Frame generation **off** for every gate-relevant number. OpenFrameGen/FSR3 results may be reported separately and are never counted against the Kakariko gate.
- `Core.sync_core_speed` on (`true`) for every run, including the baseline.

## Cache conditions

- **Cold**: pipeline disk cache and Vulkan driver cache deleted (or a fresh `--` portable cache
  directory per run). Cold runs are one cache condition, not three.
- **Warm**: the cache from a previous completed run of the same build+settings.
- Never reuse a candidate-warmed cache for a baseline cold run. Keep cache directories
  separate (`portable/sdmc`-style snapshots), and record which is which.
- A/B captures must use the same instrumentation and the same cache condition.

## Run matrix (minimum)

Per scenario × per cache condition × per build under test: **≥ 3 matched captures**.
Record each run separately; do not average runs to hide a failing one.

Scenarios:

1. **OoT landing screen** — cold and warm. Markers: process start → `Booting game:` →
   first present. Metrics: time-to-first-interactive-frame (see below), pipeline load time
   (`Nx2Boot event=shader_load_end` seconds), hitch counts.
2. **Kakariko Village, 60 s gameplay** — after a 30 s settle (let pipelines build),
   frame-gen off. Entry transition is a **separate capture**, never merged into the 60 s
   segment and never used as a substitute.
3. **One heavier area (e.g. Gerudo Valley / MK8D comparator)** — entry transition as one
   capture plus a 60 s segment as another. Reported separately, not excluded.

Fixed save and route for scenario 2/3: a fresh save at the Kakariko Minuet warp point; walk the
same loop (gate → well → around the houses → back) while a 60 s timer runs; do not interact with
anything that varies between runs.

## Capture markers

Enable in the run environment:

- `EDEN_NX2_STUTTER_TRACE=1` — per presented frame attribution; frames over 33 ms logged;
  every 10 s an `Nx2StutterSummary` (histogram of frame times, pipeline builds and lookups).
- `EDEN_NX2_STUTTER_DETAIL_MS=50` (default) — zone-level attribution for slow frames.
- `EDEN_NX2_PIPELINE_BUILD_TRACE=<file>` — before/after every driver pipeline build
  (`BEGIN`/`END` with `ms=`), plus the boot-time `SUBMIT`, `EMIT-BEG`/`EMIT-END` lines this
  branch adds. `SUBMIT → EMIT-END → BEGIN → END` per pipeline
  gives enqueue-to-usable end to end; the timestamps must be correlated per pipeline key
  (hashes are in the log lines).
- `EDEN_NX2_MEM_TRACE=1` — every 2 s: texture cache bytes, device usage, staging pools,
  process commit/working set, DXGI local/non-local budget and usage, per-heap VMA driver
  budget/usage and allocator statistics, plus sparse-page/device-buffer/render-target pools.
- The ordinary always-on lines used as boundaries: `Booting game:`, `nx2:vi2 last 600 presents`
  (nx2_gsv.h), `Total Pipeline Count:`, `Shader cache v2 boot load`, `Trimmed …`, `Buffer cache:`,
  `Native compute storage bindings:`, `CPU readback summary`.

Frame counting boundary: with frame generation off, one displayed frame == one original rendered
guest frame; count frames at the swapchain present boundary (the same boundary the
`nx2:vi2 last 600 presents` lines use). If a counter is not directly visible in a capture, the
count must be derived from the stutter-trace histograms and validated against wall time
(`sum of histogram bins == frames in window`).

## Metrics to report (per run, and per scenario mean/min/max over the ≥3 runs)

- Wall-clock start/end and capture duration.
- Frame metrics: mean real FPS; p50/p99/p99.9 real-frame **intervals** (ms) — p99.9 is noisy on
  short captures and must be flagged as such; sample counts (number of original rendered frames);
  hitch counts **> 100 ms** and **> 250 ms** and the worst interval.
- Guest game speed (sync on; report separately from FPS).
- Time-to-first-interactive-frame for OoT boot (landing screen usable).
- Pipeline timings: `Nx2Boot shader_load_end` total seconds; per-pipeline `SUBMIT→EMIT→BEGIN→END`
  distribution (count, median, p95, max) for pipelines built during the capture; blocking wait
  on pipelines (`PipelineWait` category ms and count).
- VRAM: peak and sustained driver heap budget/usage for the device-local heap (DXGI local +
  per-heap VMA), committed allocation vs live suballocation, texture/buffer/staging bytes,
  sparse-backed bytes and peak, reclaimed bytes and reallocation after reclaim (if a reclaim
  policy was tested), host peak commit/working set. Report these as estimates — never as exact
  occupancy.
- Any regression vs baseline in the heavier area.

## Tooling

`tools/nx2/cache_metrics.py` does the log side:

```
python tools/nx2/cache_metrics.py parse run1.log --session 1 > run1.json
python tools/nx2/cache_metrics.py compare --a base1.log base2.log base3.log \
    --b cand1.log cand2.log cand3.log --label-a 2.4.1 --label-b 2.5.0-candidate
```

`compare` prints a markdown table with mean/min/max of each side and the difference of the
means; per-run numbers stay in the JSONs next to the logs.

## Release gate (Kakariko route, this contract)

Each matched candidate capture must show **mean ≥ 10 real FPS and p99 real-frame interval ≤ 100 ms**
on the 60 s Kakariko route, frame-gen off, sync on, compared against a baseline run on the same
machine with the same save/route/settings. The entry transition is reported separately. If a
run misses the gate, report the miss — do not substitute a calmer route, display FPS, or an
average across runs.

## What is not allowed

- Quoting 2.5.0 gains from the five session logs shipped with this release.
- Comparing different firmware, titles, saves, routes, settings, driver or AC state as if matched.
- Baseline cold runs preceded by candidate warm caches.
- Counting frame-generated frames toward the gate.
- Claiming "2.5.0 is ready" without this contract run on the target machine; without it the
  correct status is "implemented, measured on hardware: not run".
