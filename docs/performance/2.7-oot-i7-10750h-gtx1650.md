# 2.7.0 — Ocarina of Time on the Metabox NH77DB (i7-10750H, GTX 1650 4 GB, 32 GiB)

Everything here comes from the three logs attached to the 2026-11-22 session, all three on the same
build (`9828c9d`, Veshiru v2.6.0, built `2026-11-22T04:48Z`) and the same machine: **Intel
i7-10750H (6C/12T), NVIDIA GeForce GTX 1650 (3935 MiB device-local, 3.04 GiB driver budget),
31.8 GiB RAM, Windows 11 26H2, firmware 23.0.1, NVIDIA 621.24**. Title: **The Legend of Zelda:
Ocarina of Time, 0400486024DEC000 v2.0.0**.

This document is the analysis behind the 2.7.0 changes. It is **not** a claim that the game is fixed:
nothing in it has been run on that machine yet (see "Verification status").

## The three logs

| Log | Frame generation | FPS Unlock patch | Patches applied | Frame times |
| --- | --- | --- | --- | --- |
| `veshiru_log-2.txt` | off (global default) | **disabled in Add-Ons** ("Dynamic FPS by Dark" applied) | Max Resolution, Texture Pool x2, Dynamic FPS | worst: five windows 51-94 ms average |
| `veshiru_log.txt` | **off** (`-C Renderer.frame_gen: false`) | on | Max Resolution, Texture Pool x2, FPS Unlock | one window at 59 ms, the rest 16.7 ms |
| `veshiru_log.txt.old.txt` | **on** (`MC Renderer.frame_gen: true`) | on | as above | two windows at ~100 ms |

All three otherwise share the same settings: `force_max_clock: true`, `gpu_accuracy: Low`,
`texture_cache_memory_limit: 3935`, `precache_shaders: Off`, `build_all_cached_shaders: false`,
`async_presentation: true`, `native_async_draws: Bounded`, `use_asynchronous_shaders: true`,
`use_vsync: Fifo`, `fps_limit: 0`, `nx2_frame_rate_limit: 60`, `sync_core_speed: true`,
`fast_cpu_time: Normal`, `fast_gpu_time: Boost`.

The first two are therefore a **matched frame-generation A/B**; the third differs in one more knob
(the FPS Unlock patch). Earlier notes that treated `veshiru_log.txt` as the frame-gen-on session are
wrong: the file with frame generation on is `veshiru_log.txt.old.txt` (14 `Frame generation (FSR3`
lines), and `veshiru_log.txt` has none.

## What the logs say

### Frame rate per 600 presents

`600 ÷ (seconds between two `nx2:vi2 229 present #N` lines)` is the real frame rate of the window.

| Window | `veshiru_log.txt` (FG off) | `veshiru_log.txt.old.txt` (FG on) | `veshiru_log-2.txt` (FPS Unlock off) |
| --- | --- | --- | --- |
| menus / open areas | 56.3-60.0 /s | 59.0-60.0 /s | 59.8-60.0 /s |
| first heavy window | 17.0 /s for 35.4 s | 10.2 /s for 58.6 s | 11.6-19.4 /s |
| second heavy window | 56.3 /s | 10.0 /s for 60.0 s | 15.8-19.4 /s |

Frame generation made the heavy stretch **three times longer** (119 s of ~10 fps instead of 35 s of
17 fps) with the same settings otherwise. That matches the 2.5.0 note: below ~30 real FPS the FSR3
path is overhead, not smoothness.

### The average is not the frame rate

`veshiru_log-2.txt`, per 600 presents, in order:

| Avg frame | Max frame | > 100 ms | Verdict |
| --- | --- | --- | --- |
| 51 613 µs | 1 335 465 µs | 12 | mostly 60 fps, one 1.3 s freeze |
| 67 527 µs | 2 204 524 µs | 30 | mostly 60 fps, one 2.2 s freeze |
| **93 808 µs** | **18 588 431 µs** | 30 | **10.6 fps average from ~3 freezes** |
| 67 797 µs | 2 225 346 µs | 40 | ditto |
| 74 610 µs | 1 202 990 µs | 186 | the only genuinely slow window |

570 of those 600 frames were 16.7 ms; 30 were over 100 ms and a handful lasted 1.2-18.6 s. That is
what "pacing feels normal but it says 10-18 fps" is: the pacing *is* normal, and the average is
carrying freezes. 2.7.0 makes the line say so (`N over 1 s`), because a 600-present average cannot
distinguish "every frame is 94 ms" from "three frames were seconds long".

### Where the freezes come from

All four appear in the same windows in `veshiru_log-2.txt`:

1. **On-demand pipeline builds.** `Runtime pipelines in the last 10 s: 56 built … 5844.6 ms of
   draws held for unbuilt pipelines` (58% of a 10 s window); also 2913 ms, 2778 ms, 2230 ms. The
   worker side of each build is 88-2100 ms (`Nx2Perf async_pipelines … worker emission and driver
   build`), and the GPU thread waits for the stage translation. Boot loads 1182 pipelines from 4019
   recorded; everything else is built where it is first drawn.
2. **Dispatches skipped for the frame.** `SkipUnbuiltDispatch: Compute pipeline … is still building:
   its dispatch waits, its outputs hold no earlier shader results` — nine in one frame window at
   321 s, more later. A compute dispatch that does not run leaves its output as it was: a billboard
   whose screen position is computed per frame is then drawn at the previous frame's position.
   **This is the most likely mechanism for the fairy flickering up and down sideways**, and it is
   why the flicker appears in busy scenes and not in menus. There is also a rebuild path in the
   same window (`StaleNullPointerSlot: Rebuilding compute program …`, 205 ms).
3. **CPU reads of GPU-written memory.** `CPU readback summary (10 s): 96 reads (91 sync GPU waits),
   0.38 MiB, avg/max sync wait 6878.1/139328.9 µs`; 353 reads in one window in `veshiru_log.txt`.
   Small transfers, 5-7 ms each on average, 60-140 ms at worst, and every one of them is a stall
   plus a chance to read a stale copy of a transform.
4. **The zero-page trim.** `TrimZeroPages: Trimmed 957 MiB … in 2149 ms` and `427 MiB … in 1700 ms`,
   both during gameplay. A saving of host RAM that the player pays for in frames.

Secondary, same windows: 53 `AllocateImage: … is over the memory budget; allocating it anyway`
(4 GB card, texture-cache limit set to the whole device), `CanResumeAcquire: Channel N waits on
semaphore … for 2 s` (GPU channels blocked on a semaphore the guest is late to release), and one
`TrimZeroPages` overlapping a pipeline storm.

### What is *not* wrong

- **Presentation.** `blocked on the GPU fence 0 us (max 78)`, `composite 23-31 µs` in every window
  of all three logs: the present path is never waiting on the GPU, and the pacer sleeps a vblank
  when a frame arrives early. Force maximum clocks is not implicated: the GPU is not the limiter.
- **Game speed.** Present rate never exceeds 60/s in any of the three logs (highest window: 60.0/s),
  so no session ran above 100% speed. Low fps with normal game speed is the FPS Unlock patch's
  real-time step, documented in `2.5-oot-switch2-gtx1650.md`.

## What 2.7.0 changes

1. **A per-title stability profile for Ocarina of Time** (`src/core/game_settings.cpp`,
   `core/game_settings.h`), applied at boot when the user's configuration does not already provide
   each part, never written to disk:
   - `build_all_cached_shaders` on, through a new session flag (`Settings::BuildAllCachedShaders`,
     `values.force_build_all_cached_shaders`): the whole recorded pipeline cache is built while the
     game loads and is kept built (`vk_pipeline_cache.cpp` no longer evicts unused prebuilt
     pipelines in this mode). This removes most of cause 1 and, with it, most of cause 2 — a
     dispatch cannot be skipped for a pipeline that is already built.
     The bound is the existing kept-pipeline budget: a quarter of host RAM at ~0.27 MiB per built
     pipeline (`KeptPipelinesForMemory`), so **27 962 on this machine** — the log's 4019 recorded
     records all fit and cost ~1.1 GiB of commit and ~2837 extra builds beyond the 1182 the boot
     already did. Those builds happen on the loading screen, and on a full 12 900-record cache they
     take longer than the 0.3 s boot load in these logs; that is the trade (a slow load instead of
     freezes in play), and it is why the switch is per title and reversible per session.
   - `force_reactive_flushing` and `keep_cpu_inner_invalidation` on: cause 3's stale reads stop
     being possible for the per-frame transforms read back on the CPU.
   - `EDEN_NX2_OOT_PROFILE=0` disables the profile for one session (same machine, same save, A/B in
     one evening), and the log names what was turned on:
     `Title 0400486024DEC000 runs this session with the stability profile: …`.
2. **The zero-page trim waits out gameplay** (`src/core/device_memory.cpp`,
   `Core::ShouldTrimZeroPages`): no pass while the guest is presenting a frame, passes still happen
   while paused/loading/in a menu, and under real host memory pressure (working set ≥ 1/3 of RAM)
   the pass runs once per escape interval instead of every 5-30 s: **120 s on a 32 GiB host** (this
   machine's commit has room) and 20 s on a 16 GiB one, where the trim is what keeps the commit
   bounded. Addresses cause 4.
3. **`nx2:vi2 last 600 presents` reports `N over 1 s`** next to `N over 100 ms`
   (`src/core/hle/service/nx2_gsv.h`), so the next captures say whether a low average is a slow
   game or a handful of freezes.

Not changed, deliberately: the renderer, the pipeline scheduler (2.6's audit stands — no scheduling
rewrite ships without a measurement on this machine), the VRAM policy, the frame-gen behaviour and
the present pacer. The profile is a configuration-level change plus one small trim-thread policy;
none of it is a new renderer path.

## How to verify on the NH77DB

1. Boot OoT with the profile on (default). The log must contain
   `Title 0400486024DEC000 runs this session with the stability profile: build_all_cached_shaders,
   reactive_flushing, keep_cpu_inner_invalidation` (fewer switches if you set any of them yourself),
   and `Shader cache v2 boot load … by build_all_cached_shaders` with a boot load longer than the
   previous session's 0.3 s (`… more by build_all_cached_shaders` is the count of extra pipelines
   built, ~2837 on the first boot with the log's cache).
2. Walk Kakariko (or the Castle Town market) for 60 s and grep:
   ```
   nx2:vi2 last 600 presents: frame <us> (max <us>, <n> over 100 ms, <n> over 1 s)
   Runtime pipelines in the last 10 s: <n> built … <ms> of draws held for unbuilt pipelines
   Async shaders: <n> compute dispatches skipped for unbuilt pipelines
   Trimmed <mib> MiB of all-zero guest pages …       (must not appear while you are playing)
   ```
   Target, from the 2026-11-22 logs: `over 1 s` = 0, draws held under ~200 ms per 10 s window,
   skipped dispatches near zero after the first visit to an area.
3. Same save, same route, `EDEN_NX2_OOT_PROFILE=0`: the A/B. `build_all_cached_shaders = false`
   should show the pipeline storms back (56 built in 10 s, seconds of held draws) and the flicker
   with them if cause 2 is what it looks like.
4. With the flicker, capture it: `EDEN_NX2_STUTTER_TRACE=1` (frames over 33 ms with their category)
   and `EDEN_NX2_FRAME_DUMP=<dir>` at the moment it happens — the frozen billboard in a frame dump
   plus a skipped dispatch in the log at the same present is proof; without both it stays a
   hypothesis.

## Still open on this machine

- **First-ever visit to an unrecorded area still builds pipelines.** The profile only builds what
  the cache has recorded; a new area's new pipelines are built on demand once, then recorded. A
  `precache_shaders` run (Configure → Graphics → Advanced, or the Precache button) covers the
  compute programs, not these graphics pipelines.
- **4 GB of VRAM with the cache limit at 3935 MiB** still produces `over the memory budget`
  allocations. The 2.6 budget follow (`VramPolicy`, retention) is what keeps it from thrashing;
  setting the per-game limit to 0 (Auto ≈ 2.9 GiB) or 2048-3072 remains the documented advice
  (`2.5-oot-switch2-gtx1650.md`) and is still the first thing to try if eviction shows up in a log.
- **Channel semaphore waits of 2 s** (`CanResumeAcquire`) are surfaced, not explained. They appear
  next to the pipeline storms, so they may be the same stall seen from the GPU side; a
  `EDEN_NX2_PIPELINE_BUILD_TRACE` capture in the same window would tell.
- **No hardware number is claimed.** The gate in `2.5-benchmark-contract.md` (mean ≥ 10 real FPS
  and p99 ≤ 100 ms on the Kakariko route) still has not been run on a 2.7.0 build.
