# 2.6 — performance and interface notes

2.6 is a performance-and-interface release with no speculative renderer change: three measured
CPU-path changes, one pacing fix taken from the two reference projects, and a brighter Deep
Current. Every claim below says what was run. Nothing here is a target-hardware FPS promise; the
benchmark contract in `docs/performance/2.5-benchmark-contract.md` still governs any number quoted
for a game.

## 1. Guest-clock-paced titles no longer run on Boost (frame rate)

**What.** `Core::GameSettings` holds the guest clock at Normal for the session for the two titles
that pace their own frames by `CNTPCT`, **Donkey Kong Bananza** (`040074A01BF12000`) and
**Star Fox (Switch 2)** (`0400E88025B1A000`), when the clock is inherited from the global profile
and that inherited clock is Boost. A clock set for the game itself, Overclock included, is left
alone. `Core::Timing::GetClockTicks` reads the session flag on every tick read.

**Why.** `GetClockTicks` derives the guest clock from the host wall clock in multicore and scales
it by the CPU clock target (`CPU_CLOCK_BOOST_MHZ / CPU_CLOCK_BASE_MHZ` = 1734/1020 = 1.7x). Kernel
sleeps and Ampere GPU timestamps stay at 1.0x wall time, so under Boost those titles see guest
time running 1.7x fast: a 60 Hz scene presents about 39 times a second, and Bananza measures its
own CPU frames over budget and drops to swap interval 2 (30 FPS) with vblank headroom left.

**Evidence.** This is the same defect and the same remedy as Orchid 0.12.0's
"keep Normal CPU clock for Donkey Kong Bananza and Star Fox" (MythosOfs/Orchid PR #180, from the
Eglantine lineage), which measured, on an RX 9070 XT at 1x with six alternating A/B runs:

| Title | Before | After |
| --- | --- | --- |
| Star Fox (Switch 2), flight tutorial | 25.52 ms mean frame (39.19 FPS), p95 26.7 ms | 17.18 ms (58.22 FPS), p95 17.7 ms |
| Donkey Kong Bananza, trench route | 57.75 mean FPS, 16 `swap interval 2` drops | 59.74 mean FPS, 0 drops |

Those are **their** hardware and **their** build. Veshiru's port is verified only as: the predicate
and the hold rule pass their unit tests, the setting is unchanged on disk, and the code path that
applies it is the same one that loads per-title overrides. `[verified: unit tests for the title
list and the hold rule; unverified: frame rates on the NH77DB]`

## 2. `RangeMap::Map`/`Unmap` do two tree lookups instead of four

**What.** `Common::RangeMap` is the range map behind `Tegra::MemoryManager`'s PTE-kind tracking, so
`Map`/`Unmap` run for every GPU address-space map or unmap. `InternalMap` used to walk the tree four
times per call: `lower_bound` and `upper_bound` to find the surrounding values, then again to find
the erase range. It now keeps the two iterators it already has, erases the range between them, and
inserts with a hint at that iterator. Ported from Orchid `f4edd9c8` / Eglantine `c6dd1d0214`
(goof787lord), with Orchid's randomized flat-model test.

**Measurement (this sandbox).** Standalone host harness, Debian 12 / g++ 12.2.0, `-O2 -DNDEBUG`,
3,000,000 random `Map` calls over 256 KiB of address space with one `GetValueAt` every 256 calls,
each build run three times (two passes per run):

| Build | Pass times | Median ns per `Map` |
| --- | --- | --- |
| 2.5 `range_map.h` | 1.068 / 1.046 / 1.017 / 1.014 / 1.032 / 1.022 s | 342 ns |
| 2.6 `range_map.h` | 0.681 / 0.650 / 0.637 / 0.642 / 0.644 / 0.638 s | 214 ns |

That is **37% less CPU per map** (0.39 s saved per 3M calls), and both builds end in the same map:
the digest over 2,700 sampled addresses and continuous sizes is `f7576526941254b8` for both. A
40-seed × 2000-operation randomized check against a flat model, covering map, unmap, overlap and
the continuous-size query, passes for both the old and the new header.

`[verified: the benchmark and the model check above, run here; unverified: the effect inside a
game, where the map is one cost among many]`

## 3. The interface applies its stylesheet once

`MainWindow::UpdateUITheme` read the theme file into a `QTextStream` twice: the second
`readAll()` returns nothing, and the empty result was set as the **window's** stylesheet, which
made Qt re-resolve the style of every child widget for no visual change. It now reads the sheet
once and sets it on the application, where every child inherits it.

`[verified: inspection of the call path and the Qt semantics of an empty widget stylesheet;
unverified: measured start-up or restyle time on Windows]`

## What was audited and *not* changed

- **On-demand pipeline compilation** stays the biggest stutter source on the 4 GB card
  (`docs/performance/2.5-oot-switch2-gtx1650.md`). 2.6 does not change pipeline scheduling:
  Veshiru's `PipelineBuild`/`ShaderJobScheduler` already build deferred compute and graphics
  pipelines on worker threads with priority promotion, and the two reference projects' pipeline
  work (Orchid `824c1145`, Eglantine `56881674`) describes an ownership model this tree already
  has. Shipping another scheduling rewrite without a target-machine measurement is not justified.
- **`VK_EXT_vertex_input_dynamic_state`** already decodes NVIDIA's 10-8-8-6 driver version
  (`NvidiaDriverVersion`), so the Eglantine PR #893 defect (every NVIDIA driver compared as older
  than 580.119.02, which kept vertex layouts in the pipeline key) is not present here.
- **Storage-binding reuse while GPU mappings are stable** has been in this tree since 2.3; the
  cache is a per-thread 512-set × 4-way table keyed on the address space, mapping generation,
  pointer, size word, alignment and flags.
- **Texture-cache memory limits** already clamp a user limit to the device-budget-derived
  thresholds (`TextureCache::ApplyThresholdOverrides`); the 2.5 note about an explicit 3935 MiB
  "filling the card" no longer describes this code.

## How to check it on the NH77DB

1. Set **CPU Clock** to Boost in the global profile, leave the per-game value unset, and boot
   Star Fox (Switch 2). The log carries one line:
   `Title 0400E88025B1A000 runs this session with CPU Clock at Normal: ...`.
2. Watch `nx2:vi2 last 600 presents`. With 2.5 the title sits near 25.5 ms per present with Boost;
   the expectation from the upstream report is ~17.2 ms at Normal. Record three windows before and
   after if you want the gate in `2.5-benchmark-contract.md` to cover it.
3. Set **CPU Clock** per game to Overclock: the hold must not apply (the log line stays absent).
4. `EDEN_NX2_STUTTER_TRACE=1` and `EDEN_NX2_DRAW_REUSE_PROBE=1` remain the tools for the pipeline
   and draw-preparation costs; neither is changed by 2.6.
