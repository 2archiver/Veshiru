# Veshiru 1.7 validation and release gate

**Candidate only.** The baseline is v1.6.0 at
`757a96e5259d3245ad2681066495cebf7cabcf6d`. PR #14 staged the 1.7 changes before the version bump.
The candidate is now prepared as `1.7.0` for an artifact-only packaging check. This is not a release
or evidence that the gates below have passed.

## Measured scope: directory discovery

Paired runs on the same Debian 12 x86-64 sandbox (2 logical CPUs, GCC 12.2, C++20 `-O2`, local
filesystem), using the baseline and candidate headers with the same driver
[`game_discovery_bench.cpp`](../../tools/integration/game_discovery_bench.cpp).
The fixture contains 100 loose folders with `base/exefs/main` and `main.npdm`, 320 unrelated files
at each game's root, and 10 flat `.nsp` placeholders. These are empty files, not playable content.
Each mode used one warm-up and 30 timed scans per build, in three alternating baseline/candidate
batches. The milliseconds below are ranges across those batches.

| Directory-only workload | Baseline median | Candidate median | Baseline p95 | Candidate p95 | Equal outputs |
| --- | ---: | ---: | ---: | ---: | --- |
| Shallow | 10.70–10.96 | 0.65–0.68 | 11.04–14.96 | 0.70–1.05 | 110 candidates, 201 watched directories |
| Deep | 13.23–13.42 | 12.86–13.43 | — | — | 110 candidates, 301 watched directories |

A counting interposer recorded `readdir` calls (including end-of-iteration): 1,007,903 → 3,503
per batch of 31 shallow scans. The change skips enumeration after checking recognized loose layouts
in immediate child folders; it does not skip probing those layouts or their updates. Deep results
overlap. **This is not a process startup, full game-list population, renderer, or gameplay benchmark.**

### Reproduce without a game dump

From the repository root in a POSIX shell:

```sh
base=757a96e5259d3245ad2681066495cebf7cabcf6d
work=$(mktemp -d)
mkdir -p "$work/base/qt_common/game_list"
git show "$base:src/qt_common/game_list/discovery.h" > "$work/base/qt_common/game_list/discovery.h"
c++ -std=c++20 -O2 -I"$work/base" tools/integration/game_discovery_bench.cpp -o "$work/baseline"
c++ -std=c++20 -O2 -Isrc tools/integration/game_discovery_bench.cpp -o "$work/candidate"
python3 - "$work/fixture" <<'PY'
from pathlib import Path
import sys
root = Path(sys.argv[1])
for i in range(100):
    game = root / f"fixture-{i:03d}"
    exefs = game / "base" / "exefs"
    exefs.mkdir(parents=True)
    (exefs / "main").touch()
    (exefs / "main.npdm").touch()
    for j in range(320):
        (game / f"asset-{j:04d}.bin").touch()
    if i < 10:
        (root / f"fixture-{i:03d}.nsp").touch()
PY
for mode in shallow deep; do
    "$work/baseline" "$work/fixture" "$mode"
    "$work/candidate" "$work/fixture" "$mode"
done
```

## Verified Open-Frame-Gen input

The compiled FP16 array is derived from
[`nano_v17_best.pth` at Open-Frame-gen `05f0706`](https://github.com/Deadly-pro/Open-Frame-gen/blob/05f0706fd92d627ba5b7a09934dafae053ea53b4/checkpoints/nano_v17_best.pth).
The corresponding [upstream MIT notice](../../third_party_notices/Open-Frame-gen.txt) and the
[RIFE](../../third_party_notices/RIFE.txt) and [Practical-RIFE](../../third_party_notices/Practical-RIFE.txt)
notices are included in the release packaging step. Only the derived weights are built in; the
checkpoint is not bundled or downloaded at build time or runtime.

With a local copy of the pinned checkpoint, run
`python3 -I tools/nx2/verify_open_frame_gen_weights.py /path/to/nano_v17_best.pth`.
The tool checks the input hash before reading its tensor state, folds the adjacent convolution and
BatchNorm layers using epsilon `1e-5`, lays out the layers in the order used by the shaders, and
compares the little-endian FP16 values. It matched **87,995 values byte-for-byte**. Packed SHA-256:
`306d7d38f46a9cfdc2f27b65c145cff268d8fde7802b4fdd5c576054e5201feb`.
This establishes weight provenance, not inference quality or performance on any GPU.

## Focused sandbox checks

- Catch2: 14 cases / 176,137 assertions for logging and launch arguments, cache sidecars,
  transport-independent title matching, frame-generation pacing/selection/capability, allocation keys and weight
  decoding. A separate loopback suite passed 4 cases / 35 assertions for HTTP limits, redirect
  rejection, cancellation, cooldown, API matching and keeping credentials off asset requests.
- The stdio probe passed UTF-8, split/merged output, file flush, unread/broken pipes and shutdown.
  The discovery regression and all 12 NX2 cache-metrics parser tests passed.
- The changed Qt sources passed syntax checks against Qt 6.8.3 headers and generated UI headers,
  including the experimental artwork path. The six Open-Frame-Gen shaders compiled to SPIR-V;
  the modified Linux renderer/presentation, startup probe and NX2 service sources passed targeted
  C++ syntax checks. The low-level console/logger/probe sources cross-compiled to AMD64 Windows
  objects. None of these checks linked or ran the Windows frontend or submitted a GPU frame.

## What is not yet validated

| Gate | Evidence still needed |
| --- | --- |
| Production build and package | Clean Windows x86-64 clang-cl 22/MSVC SDK + Qt 6.8.3/Ninja/Vulkan SDK build, full `ctest --test-dir build --output-on-failure --no-tests=error`, PE header and installed Qt plug-ins, license/secret review and SHA-256 for packaged files. The Linux configure attempt did not retrieve the pinned Boost 1.92.0 release asset; focused compilation does not substitute for the supported build. |
| Native console | On Windows 10/11 test cmd.exe, PowerShell/Windows Terminal, Explorer, merged and separate redirects, an unwritable `--log-file`, `--no-console`, Ctrl+C/Break while probing/playing, missing keys/firmware/driver failure, and orderly exit with an unread pipe. Check the log snapshot for partial lines, usernames, private paths and credentials. |
| Matched performance | Same Windows host, driver, display/refresh, resolution, accuracy, audio, power plan, and supported legal scene on both builds. Match cold vs warm cache state and settings (including FG off for the base comparison). Record time to frontend ready and full library scan, real-game FPS and frame-time percentiles (p99/p99.9 for low FPS), renderer CPU/GPU time, RAM/VRAM, shader/pipeline hits/build time, and stutters using an explicitly stated threshold. Alternate multiple runs and report dispersion and any regressions. |
| Frame generation | At fixed base simulation settings, capture separate real-frame, generated-submit and displayed-present results; include display intervals, input latency and audio/simulation rate. Test the available NVIDIA and Intel Vulkan devices, unsupported API/format fallback, live toggles, alt-tab, resize/fullscreen, HDR-to-SDR, device loss/reset, overlays and capture. No visual, vendor, VRR/VSync or latency claims were verified in the sandbox. |
| Artwork | The [documented API v2](https://www.steamgriddb.com/api/v2) has an authenticated search/icons protocol, but the [terms](https://www.steamgriddb.com/terms) restrict automated use and redistribution. Confirm API use and local caching/attribution with the provider before enabling it for distribution. Verify live response/CA/CDN behavior, user cancellation and window-close during lookup, offline legacy cache, and switchable fallback on the supported build. No live provider requests were tested. |

The two supplied v1.6 diagnostics are not an FG A/B. One includes Open-Frame-Gen; the DK Pass run
had frame generation **off**. Both contain AES initialization assertions and unmapped GPU-read
errors. They do not isolate a cause or measure display frame-time lows. Keep those private logs and
any benchmark captures out of the repository.

For an operator-controlled attached test, use the existing [NX2 trace guidance](../nx2/debug-mcp.md)
and cache tooling under `tools/nx2/`. Do not start, stop or inject into another user's emulator.
Report game, scene, build IDs, public hardware/driver details, the settings above, and aggregated
results rather than sharing keys, dump paths or full captures.

Use `build-check` and the `release-binaries` package validation run (`publish_release=false`) on
the candidate SHA. Verify both Windows variants, their `--version` output, and archive checksums.
Do not publish until the Windows and hardware gates pass and publication is explicitly requested.
Keep 1.7.1 performance ports separate from the 1.7.0 candidate. No Lichii code is included:

- Upstream Lichii [#2100](https://github.com/zortos293/Lichii/pull/2100) is a candidate for the
  **static** driver cache; Veshiru's per-title driver cache already replaces files atomically.
  Test Windows cache replacement, driver rejection, and device-loss behavior before adapting it.
- Upstream [#2163](https://github.com/zortos293/Lichii/pull/2163) is a separate buffer-lifetime
  candidate. Inline-index growth and retirement need the regression test, not an FPS claim.
- Leave async defaults, compute-pass skipping, and the fork's NVIDIA shader routing, layout
  sharing, and empty-texture shortcuts unchanged until matched driver runs check rendering,
  cache invalidation, and lifetimes. Do not enable full boot precaching by default or copy the
  fork's Linux-only `malloc_trim` change to Windows.
