# Operator checklist — 2.5.0 on the Metabox NH77DB (GTX 1650)

Everything in this file is for the target machine. Nothing here can be validated in CI or a
Linux sandbox. Expected time: 90–120 minutes with a fresh firmware and save.

## 0. Ground rules

- Do not change the title, version, save, route, settings, firmware, driver, or AC/output state
  between the baseline and the candidate. Record them all.
- Keep `Core.sync_core_speed = true` everywhere, including the baseline.
- Frame generation off for all gate-relevant runs (`Renderer.frame_gen = false`).
- Record the GPU driver (`nvidia-smi --query-gpu=driver_version --format=csv`) and the
  firmware version line from the log (`SetFirmwareVersion`).

## 1. Build and install

1. Download the 2.5.0 zip (`veshiru-windows-x86_64-pgo.zip`) and `SHA256SUMS.txt` from the
   release; verify the hash.
2. Extract; run `veshiru.exe` once.
3. Confirm the About dialog reports `Veshiru 2.5.0`.

## 2. Fresh-profile checks (first boot)

1. Let it create the profile; open Configure → Core. **Synchronize Core Speed must be on**
   out of the box. `%APPDATA%\Veshiru\config\settings.ini` must contain
   `Core\sync_core_speed\default = true` (or absent with recommended defaults on — both are
   conforming).
2. `settings.ini` for the **global** config kept from 2.4.1: if it contains
   `Core\sync_core_speed\default = false` from an older install, the stored `false` is kept
   on purpose. Verify `Apply recommended settings` flips it to `true`. If you want a one-time
   migration of stored `false`, that is a maintainer decision — do not hand-edit files to
   "fix" them and then call it verified.
3. Per-title override test: open the HOME Menu's 0100000000001000 per-title config
   (`custom\0100000000001000.ini`) if it exists. Its `sync_core_speed` value decides for the
   HOME Menu, independently of the global setting — this is expected. Record what it contains.
4. Delete-or-rename the per-title config, relaunch, confirm the HOME Menu now runs with sync
   on (log line `MC Core.sync_core_speed: true` next to `Booting game: 0100000000001000`).
5. Repeatable-timer check: with sync on, load a scene with a repeatable in-game timer
   (OoT intro clock) and compare game speed against wall time for 60 s; note the ratio.
   Then load one overloaded scene (heavier area) and note whether guest speed visibly drops
   below 1.0 — sync on must make the guest *slow down*, never run ahead.

## 3. News applet (HOME Menu)

1. Fresh `news_images` cache (rename `<config>\image_cache\news` if present) — or delete it.
2. Open the HOME Menu news applet (quick news tile, then the full applet). The tile and the
   applet must render the Veshiru icon, not a blank or another project's artwork.
3. If the icon is missing: note the exact surface (tile vs applet vs both), keep the log, and
   check for `news:` lines (`news: 14 entries loaded from cache`, `news: N entries updated
   from GitHub`) and for `GetTopicList` (`news: topic list requested; advertising veshiru`).
   A nearby `(STUBBED)` line is not proof the icon path is broken.
4. Relaunch and confirm it still renders (cache rebuild path).

## 4. Discord (documentation-level check only)

1. With Discord running, start OoT; hover the activity: it shows the application as registered
   by that client ID — **"Eden"**. This is expected in 2.5.0 and is a known issue; details and
   opt-out (Configure → Web) are in the changelog.
2. Confirm the activity text is Veshiru ("Playing The Legend of Zelda: Ocarina of Time",
   "Veshiru 2.5.0 – Version 2.0.0") and the large image is the Veshiru logo.
3. Do not call this "Discord shows Veshiru" in any report — only the application name is wrong.

## 5. Performance runs (follow docs/performance/2.5-benchmark-contract.md)

For each numbered scenario and cache condition, capture ≥ 3 runs. Same order every time.

1. **Environment**: set `EDEN_NX2_STUTTER_TRACE=1`,
   `EDEN_NX2_STUTTER_DETAIL_MS=50`,
   `EDEN_NX2_PIPELINE_BUILD_TRACE=%USERPROFILE%\veshiru-trace.log`,
   `EDEN_NX2_MEM_TRACE=1`. Use fresh portable cache directories per cold run.
2. **Scenario A — OoT landing screen, cold**: boot OoT with a wiped cache; note
   time-to-first-interactive-frame (from `Booting game:` to the first `nx2:vi2` present that
   shows the landing screen interactive), `Nx2Boot event=shader_load_end`, and the number of
   hitches > 100 / > 250 ms during the first 60 s after boot.
3. **Scenario A — OoT landing screen, warm**: same, with the cache from step 2 kept.
4. **Scenario B — Kakariko 60 s**: from a Minuet-of-time save-warp into Kakariko, settle 30 s
   (no capture), then a 60 s capture walking gate → well → houses → gate. Frame-gen off,
   sync on. Record presents window lines, `Nx2StutterSummary` lines, and run
   `python tools/nx2/cache_metrics.py parse` on the log.
5. **Scenario C — heavier area**: one area clearly heavier than Kakariko (e.g. Gerudo Valley
   or a MK8D race comparator). Entry transition as its own capture, then a 60 s capture.
6. **VRAM**: during scenario B, keep `EDEN_NX2_MEM_TRACE=1` on; record the peak/sustained
   device-local heap, the texture-cache vs driver accounting, and whether any sparse-bind or
   `Trimmed …` activity overlaps the capture window.
7. **A heavier entry transition** (OoT: Kakariko first entry after boot): separate 10–30 s
   capture; note the worst frame, the number of pipelines built during it
   (`Runtime pipelines in the last 10 s`), and whether draws were held
   (`Async shaders: … draws` / `pipeline_wait` categories).

## 6. Smoke tests (Windows/Vulkan)

1. Cold boot → HOME Menu → launch OoT → save/load a game save → quit to HOME → navigate menus → close.
2. Repeat with a MK8D boot.
3. No crashes, no hangs, no missing save data. Note exact steps.

## 7. Report back (attach to the performance doc or PR)

- Collected logs (the Veshiru log file plus `veshiru-trace.log`).
- For each scenario: mean real FPS, p50/p99/p99.9 intervals, sample counts, hitch counts
  (>100/>250 ms), worst interval, guest speed.
- Pipeline `SUBMIT→EMIT→BEGIN→END` medians and maxima for pipelines built in the capture window.
- Peak/sustained device-local heap; reclaim events if any.
- Pass/fail against the gate: mean ≥ 10 real FPS and p99 ≤ 100 ms (Kakariko route).
- Anything that looked wrong (visual glitches, saves not persisting, applet blank), even if minor.
