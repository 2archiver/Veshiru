# 3.2.0 — what the three 2026-11-26 logs say

This is the analysis behind the 3.2.0 work. It is **not** a claim of an FPS gain: the changes below
were made from these logs alone, and nothing here has been measured on the reference machine yet.
"Verified" in this document means "the log says so", never "the fix was benchmarked".

## The three logs

| Log | Emulator | Machine | Title | What it is here for |
| --- | --- | --- | --- | --- |
| `ve3shiru_log.txt` | Veshiru v3.1.0, `619081d` | i5-12450H (4 P + 4 E, 12 threads), 23.7 GiB, GTX 1650 (3935 MiB), Windows 11 25H2 | Yoshi and the Mysterious Book (`0400245021D2C000`) | the shadow tester's report: FPS drops "when performing certain actions" |

| `eden_log.txt.old.txt` | Lichii `nx2-build-386` | i7-10750H, 31.8 GiB | Super Mario Galaxy 2 (`0100FD8022DAA000`) | a Lichii comparison point, not a Veshiru run |

## Yoshi and the Mysterious Book: where the frames go

The session runs 4.2 s to 275 s, presents 13,200 frames, and the steady state is healthy: 17-18 ms
per frame, 0-3 frames over 100 ms per 600 presents from 117 s on. The drops the report mentions are
not spread across the session; they sit in four places, and none of them is shadow rendering.

1. **A 5.7 s all-zero guest page trim while the game was running.** At 92.6 s the log records
   `Trimmed 11277 MiB of all-zero guest pages out of 15858 MiB resident in 5738 ms`. The trim
   thread is `Low` priority, but the pass reads every resident guest page and takes the VAD lock
   every 2 MiB, and the same window records frames of 2.64 s and `3 over 1 s`. Thirty seconds
   later the thread logs `Deferring the all-zero guest page trim while the game runs (a pass takes
   1-2 s)`, so the guard that was supposed to keep this out of gameplay had already been
   overridden once: with 23.7 GiB of RAM the host was classified as "tight" (the cut-off was
   24 GiB) and the guest was presenting, so the 20 s memory-pressure escape let a whole pass run.
2. **CPU readbacks waiting on the GPU thread.** Per 10 s window the session does 190-1,460 guest
   reads of GPU-written memory; 0-232 of them pay a synchronous wait for the GPU thread to run the
   flush, 268 µs to 2.7 ms on average and up to 73 ms. In the worst window (34.6 s) 199 of 396
   reads waited, 530 µs each, about 105 ms of the 10 s. This is emulator-to-GPU synchronisation,
   not shadow work.
3. **Graphics pipelines translated on the GPU thread behind a >8 MiB texture descriptor pool.**
   `Texture descriptor pool of 16777216 bytes: pipelines that use it translate on the GPU thread`
   appears once, and each new pipeline in that scene costs 2.7 ms of GPU-thread time
   (`Graphics pipeline built on the GPU thread in 2.7 ms`). Only 5 runtime pipelines were built
   in the session, so this is a load-time cost here, not a gameplay one.
4. **The first video decode and the first composite** (8.2-17.4 s) take seconds: `present #2` waited
   4.2 ms and `present #4` 5.5 ms, and the 6.18 s worst frame belongs to that start-up window.

Shadow rendering does not appear in the log as a fault: no rejected shadow program, no
`Draw skipped (no pipeline)` line, no depth or ZCULL error during gameplay (the two
`ZBCQueryTable: invalid depth index` lines are at 7.97 s, before the first present, and yuzu-family
emulators answer them with `BadParameter` by design). Nothing in the 3.2.0 change set touches
shadow-visible state, so shadow output cannot change: no shader, sampler, depth or render-pass
behaviour was edited.

### What 3.2.0 changes for it

- The trim pass is bounded to 512 MiB per slice when the guest is presenting, and the slices stop
  as soon as the guest pauses (`src/common/host_memory.cpp`, `src/core/device_memory.cpp`). The
  5.7 s freeze becomes a series of sub-frame slices; the pages trimmed in one slice are no longer
  resident, so the next slice continues past them. The "ample RAM" cut-off also moves to 20 GiB so
  this host is no longer treated as tight.
- The GPU thread pinning warning in this log (`skipped: 4 physical performance cores, needs 6`) is
  acted on: front and back now take a performance core each on 4 P-core hybrids.
- The native compute binding counters that this log shows running unconditionally (371,040
  bindings in one window) now need `EDEN_NX2_BINDING_STATS=1`.

### What 3.2.0 does not fix

- The readback waits in (2). They are the split GPU design working as intended: a guest read of
  GPU-written memory has to wait for the GPU thread to reach a draw boundary. Widening the windows
  where the GPU thread services sync requests is a larger change and needs a trace with
  `EDEN_NX2_GPU_PROFILE=1 EDEN_DKB_FRAME_TRACE=1` before it is attempted.
- Pools above 8 MiB still translate their pipelines on the GPU thread (3). Raising the cap only
  moves the cost of flushing the pool from one place to another; it needs a measurement of the
  flush against the translation win, which this log does not contain.

## Mario Kart World: the 3.2 reference run

3.1.0 on the reference machine is GPU-bound in races, not CPU-bound: the presentation window shows
`600 ran a frame ahead` with `blocked on the GPU fence 0 us`, and the frames themselves are 17-81 ms
depending on the course section. The CPU side of the same session:

- **Pipeline work is the largest CPU cost.** Per 10 s window: 15-310 graphics pipelines built,
  50-676 ms of GPU-thread time, of which 20-452 ms is the GPU thread waiting for stage translation
  on workers, and 4-170 ms of draws held for unbuilt pipelines. The worst windows (44.1 s, 0.7 s of
  pipeline work per 10 s) coincide with `310 built ... 290 new`, i.e. first visits to a course
  section, and with the shader cache warming up.
- **Readback waits are the second cost.** 54-759 synchronous waits per 10 s, 155 µs to 4.8 ms on
  average, and one 1.31 s wait in the 156 s window. About 16% of that window is spent blocked.
- **VRAM stays inside the budget**: 256-380 MiB of buffer cache, texture thresholds 1.4-2.3 GiB
  expected against 2.8-3.2 GiB critical, `Host memory: 27582 MiB of commit left`.

The log cannot separate "Veshiru renders this scene more slowly" from "the GTX 1650 is saturated":
there is no GPU-time breakdown in it (`EDEN_NX2_GPU_PROFILE` was off). Comparing against Satsuma
Build 94 therefore needs a run with the profile on, on the same course and the same settings, and
this document does not claim a result. 3.2.0 does not change any rendering path, so a large FPS
delta against 3.1.0 is not expected; the pinning and the trim change above are the only changes that
can move frame time in a race.

## Lichii: the comparison log

`eden_log.txt.old.txt` is a Lichii build that cannot load the title at all:
`NUP container has no package with a usable ExeFS` four times, then `Failed to load ROM (Error 69)`
after 14.6 s. The same container loads in Veshiru 3.1.0, so this log contributes no Veshiru
regression and no port candidate; it is kept here as the record of why the Lichii NUP path was not
taken as a reference.
